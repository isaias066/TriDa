# RNF-001 — Rendimiento de Procesamiento

**Tipo**: Requisito No Funcional de Rendimiento

## Descripción

En condiciones normales de operación, el sistema debe procesar cada transacción simulada y determinar su score de riesgo en menos de 2 segundos. Este rendimiento es adecuado para un entorno académico y de demostración, con carga reducida y sin exigencias de producción bancaria.

## Requisitos Específicos

**RNF-001.1** — El sistema debe procesar cada transacción simulada y calcular su score de riesgo en menos de 2 segundos en operaciones comunes.

**RNF-001.2** — El objetivo de rendimiento aplica a un entorno académico y de demostración, no a una carga transaccional equivalente a la de un banco real.

**RNF-001.3** — En esta versión Beta no se garantiza una latencia inferior a 500 ms por transacción, ya que no corresponde al alcance del prototipo.

**RNF-001.4** — El sistema debe mantener un desempeño estable durante ejecuciones extendidas del generador de transacciones.

**RNF-001.5** — Durante ejecuciones prolongadas no deben presentarse degradaciones notorias del dashboard, bloqueos inesperados ni interrupciones del flujo principal.

# RNF-002 — Concurrencia Limitada y Operación de Usuario Único

**Tipo**: Requisito No Funcional de Rendimiento

## Descripción

El sistema está diseñado para operar bajo un modelo de usuario único y con concurrencia limitada. No se exige soporte multiusuario ni arquitectura distribuida en esta etapa MVP.

## Requisitos Específicos

**RNF-002.1** — El sistema debe operar bajo un modelo de usuario único durante la demostración.

**RNF-002.2** — No se exige ni se garantiza soporte para múltiples usuarios simultáneos, múltiples sesiones concurrentes o balanceo de carga.

**RNF-002.3** — La arquitectura del MVP no incluye microservicios, contenedores, escalabilidad horizontal ni infraestructura distribuida.

**RNF-002.4** — La concurrencia del sistema debe limitarse al pipeline interno: `Generación → Análisis → Alerta → Registro`.

**RNF-002.5** — El flujo interno debe ejecutarse de forma secuencial o con un paralelismo mínimo controlado.

**RNF-002.6** — El diseño debe prevenir inconsistencias en la base de datos local y colisiones de registros durante el procesamiento.

# RNF-003 — Seguridad Básica

**Tipo**: Requisito No Funcional de Seguridad

## Descripción

El sistema debe implementar medidas de seguridad esenciales y adecuadas para un prototipo académico, priorizando la validación de entradas y la protección básica del entorno local.

## Requisitos Específicos

**RNF-003.1** — El sistema debe validar y sanear los datos de entrada antes de procesarlos.

**RNF-003.2** — El sistema debe implementar protección básica contra ataques frecuentes, como inyección SQL, ingreso de datos corruptos y manipulación del dashboard.

**RNF-003.3** — El sistema puede utilizar HTTPS cuando el entorno local lo permita, sin requerir certificados digitales formales en esta etapa.

**RNF-003.4** — Los archivos de configuración sensibles, como credenciales básicas de base de datos y parámetros del modelo, deben mantenerse protegidos.

**RNF-003.5** — Esta versión no exige controles de seguridad enterprise como cifrado AES-256 obligatorio, gestión profesional de claves, controles avanzados de intrusión o TLS mutuo.

**RNF-003.6** — Las medidas de seguridad implementadas deben ser suficientes para un entorno de desarrollo y demostración, pero no se consideran equivalentes a las de un sistema bancario de producción.

# RNF-004 — Disponibilidad para Demostración

**Tipo**: Requisito No Funcional de Disponibilidad

## Descripción

El sistema no está diseñado para operación continua 24/7 ni para cumplir niveles de disponibilidad bancarios. Su disponibilidad esperada corresponde al uso en demostraciones, pruebas de validación y ejecución supervisada.

## Requisitos Específicos

**RNF-004.1** — El sistema no está obligado a garantizar disponibilidad continua 24/7.

**RNF-004.2** — El sistema no está obligado a cumplir acuerdos de disponibilidad bancaria del 99.5 % o superiores.

**RNF-004.3** — La disponibilidad esperada debe ser suficiente para demostraciones, pruebas de validación y ejecución del flujo simulado bajo supervisión.

**RNF-004.4** — Si el sistema requiere reiniciarse manualmente durante una demostración o prueba, esto se considera aceptable dentro del alcance del MVP.

**RNF-004.5** — Si el dashboard requiere actualización manual en algún momento, esto también se considera aceptable dentro del alcance del prototipo.

# RNF-005 — Mantenibilidad

**Tipo**: Requisito No Funcional de Mantenibilidad

## Descripción

El sistema debe estar desarrollado con una estructura modular que facilite ajustes y mantenimiento durante su evolución académica y técnica.

## Requisitos Específicos

**RNF-005.1** — El código debe estar modularizado para permitir ajustes en los umbrales de riesgo.

**RNF-005.2** — El código debe estar modularizado para permitir ajustes en los parámetros del generador de transacciones.

**RNF-005.3** — El código debe estar modularizado para permitir ajustes en la arquitectura del modelo.

**RNF-005.4** — El código debe estar modularizado para permitir ajustes en la configuración básica de la base de datos.

**RNF-005.5** — El sistema debe contar con documentación suficiente para su uso académico y demostrativo.

# RNF-006 — Portabilidad

**Tipo**: Requisito No Funcional de Portabilidad

## Descripción

El sistema debe poder instalarse, ejecutarse y evaluarse en equipos de uso académico comunes, sin requerir hardware especializado ni licencias costosas.

## Requisitos Específicos

**RNF-006.1** — El sistema debe ser compatible con entornos de desarrollo comunes como Windows 10, Windows 11 y distribuciones Linux usadas por estudiantes o laboratorios.

**RNF-006.2** — El prototipo debe poder instalarse utilizando dependencias estándar del entorno de desarrollo.

**RNF-006.3** — Las dependencias estándar contempladas incluyen Python, bibliotecas de aprendizaje automático, `pip` o `venv`, un motor de base de datos local y Node.js si se requiere el dashboard.

**RNF-006.4** — El sistema no debe requerir hardware específico, sensores externos ni infraestructura especializada para su funcionamiento.

**RNF-006.5** — El sistema no debe depender de licencias corporativas o herramientas de alto costo para su instalación y evaluación.

# OR-001 — Formato del Score

**Tipo**: Otro Requisito

## Descripción

Los scores de riesgo deben expresarse de forma clara y consistente para facilitar la interpretación durante el análisis de transacciones.

## Requisitos Específicos

**OR-001.1** — Todo score de riesgo debe expresarse como porcentaje con un decimal.

**OR-001.2** — El formato esperado para la visualización del score es similar a: `85,5 %`.

**OR-001.3** — El formato del score debe mantenerse consistente en dashboard, alertas, reportes y registros históricos.
